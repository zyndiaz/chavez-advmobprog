# Laboratory 6 Discussion

## Chat Feature and Real-Time Messaging

In this part of Laboratory 6, I added a chat feature to the application's bottom navigation. The chat list displays registered Firebase users other than the currently signed-in user, and its search field filters the list by name or email. Selecting a user opens a one-to-one conversation. This makes it possible to find a conversation partner without showing the current user's own account as a chat option.

The chat feature uses Cloud Firestore to keep user discovery and messages synchronized. A small `chat_directory` document stores the UID, name, username, and email needed by the chat list, while the full profile remains in the private `users` collection. When a user signs in or opens Chats, the app synchronizes that user's directory entry. Messages are stored under a chat-room document whose ID is made from the two user IDs in sorted order. This gives both participants the same room ID, regardless of who starts the conversation. Each message records its sender, receiver, text, timestamp, and status. Firestore snapshots allow new messages and status changes to appear in the open conversation without manually refreshing it.

The conversation screen distinguishes sender and receiver bubbles, animates messages as they appear, and provides a text composer with sending feedback. The app also records delivered and seen states. In the current implementation, opening the conversation marks all incoming messages as seen; it does not wait for each individual message bubble to become visible. Delivered and seen both use double-check icons, with color indicating the seen state, so clearer labels or distinct icons would make the status easier to understand.

One important part of completing the feature was configuring Firestore security rules. User profiles should not be publicly readable just to populate the chat list, so the app uses the limited chat directory instead. The rules allow signed-in users to read that directory while restricting each directory write to its owner, and they limit conversation access to its two participants. During testing, a permission-denied error showed that the updated rules must be published to the same Firebase project used by the app. After deployment, testing with two Firebase accounts verifies that both users appear in the directory, the current account is excluded from its own list, search finds the other account, and sent messages appear in the conversation. This activity demonstrated that real-time messaging depends on both the client-side stream and the corresponding database structure and access rules.
